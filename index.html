ที่มาของปัญหา 1: ช่องว่างความเร็วระหว่าง CPU กับ RAM (The Memory Wall)

Slide 03 / 26
📈 ทำไมหน่วยความจำหลัก (DRAM) จึงเป็นคอขวดสำคัญที่สุด?
  • ตลอด 20 ปีที่ผ่านมา จำนวนแกนประมวลผล (CPU Cores) และความเร็วในการคำนวณเติบโตขึ้นอย่างก้าวกระโดด
  • ในทางกลับกัน ความเร็วในการเข้าถึงข้อมูลชุดแรกของ DRAM (Access Latency) แทบไม่ลดลงเลย โดยยังคงอยู่ที่ประมาณ 40–50 นาโนวินาที
  • เมื่อซีพียูเพิ่มจาก 1 คอร์ เป็น 8–64 คอร์ ทุกคอร์ต่างแย่งกันส่งคำขอผ่านช่องทางหน่วยความจำ (Memory Channel) ที่ใช้ร่วมกัน
  • หากตัวควบคุมหน่วยความจำ (Memory Controller) จัดการลำดับคำขอได้ไม่ดี ซีพียูที่เร็วที่สุดก็ต้อง หยุดรอข้อมูลเฉยๆ (CPU Stall) กว่า 50–70% ของเวลาทั้งหมด
📊 แผนภาพเปรียบเทียบการเติบโตของ CPU Throughput vs. DRAM Latency
อ้างอิงแนวคิดพื้นฐาน: Wulf & McKee, "Hitting the Memory Wall: Implications of the Obvious," ACM SIGARCH 1995 Slide 03 / 26

ที่มาของปัญหา 2: การปะปนของคำขอ (Request Interleaving) ทำลาย Locality

Slide 04 / 26
🔄 ปรากฏการณ์ Request Stream Interleaving คืออะไร?
  • เมื่อทำงานคอร์เดียว (Single-Core): โปรแกรมมักอ่านข้อมูลที่เรียงต่อกันในแถวเดียวกันของ RAM เช่น Row A → Row A → Row A ทำให้ได้ข้อมูลจาก Row Buffer ทันที (Row Hit)
  • เมื่อทำงานหลายคอร์พร้อมกัน (Multi-Core): แม้แต่ละคอร์จะอ่านแถวเดิมของตัวเอง แต่เมื่อคำขอไหลมารวมกันที่คิวของ Memory Controller ลำดับคำขอจะสลับกันเป็น Row A → Row B → Row C → Row D
  • ผลเสียร้ายแรง: ทุกครั้งที่สลับแถว ฮาร์ดแวร์ต้องสั่งปิดแถวเก่าแล้วเปิดแถวใหม่ซ้ำไปมาไม่สิ้นสุด เรียกว่า Row-Buffer Thrashing
🎨 แผนภาพเปรียบเทียบ: ลำดับคำขอก่อนและหลังผ่านการรวมคิว
อ้างอิงการค้นพบของ Awasthi et al., "Prediction-Based DRAM Row-Buffer Management in the Many-Core Era," PACT 2011 Slide 04 / 26

ที่มาของปัญหา 3: การถูกทำลายของความขนานระดับแบงก์ (Bank-Level Parallelism)

Slide 05 / 26
⚡ ความขนานระดับแบงก์ (BLP) ช่วยซ่อนเวลาแฝงของ RAM อย่างไร?
  • หน่วยความจำ DRAM 1 แถว (Rank) ถูกแบ่งออกเป็น 8 ถึง 16 แบงก์อิสระ (Independent Banks) ที่สามารถทำงานขนานกันได้พร้อมๆ กัน
  • หาก Thread A ต้องการข้อมูล 2 ชิ้นที่อยู่ใน Bank 0 และ Bank 1 ซีพียูจะส่งคำขอทั้ง 2 ออกไปพร้อมกัน ताकिซ้อนทับเวลาทำงานกัน (ใช้เวลาหยุดรอเพียง 1 รอบของ DRAM)
  • แต่เมื่อมี Thread B เข้ามาแทรกเฉพาะที่ Bank 1: คำขอชิ้นที่ 2 ของ Thread A จะถูกเลื่อนออกไป ทำให้ Thread A ต้องหยุดรอเป็น 2 เท่าของเวลาปกติ (Serialization Stall)!
⏱️ แผนภาพเปรียบเทียบเวลาที่ซีพียูต้องหยุดรอ (CPU Stall Time)
อ้างอิงทฤษฎีความขนานระดับแบงก์: Mutlu & Moscibroda, "Parallelism-Aware Batch Scheduling," ISCA 2008 Slide 05 / 26

🎯 วัตถุประสงค์ของงานวิจัย (Research Objectives)
  • เพื่อออกแบบสถาปัตยกรรม AP-PARBS ที่ผสาน Adaptive Page-Mode Prediction เข้ากับ Parallel Request Scheduling
  • เพื่อพัฒนาเทคนิค Queue-Lookahead Precharge Inhibition (QAPI) ป้องกันการสั่งปิดแถวผิดจังหวะเมื่อยังมีคำขอแถวเดียวกันรอในคิว
  • เพื่อลดเวลาแฝงเฉลี่ยของ DRAM และเพิ่มทั้ง Throughput กับความเป็นธรรม (Fairness) ในระบบ Multi-core
💡 สมมติฐานการวิจัย (Research Hypothesis)

"เมื่อตัวควบคุมหน่วยความจำจัดกลุ่มคำขอของเธรดเดียวกันให้ทำงานขนานกันข้ามแบงก์ (Parallel Scheduling) และใช้ตัวพยากรณ์ที่ตรวจสอบคิวล่วงหน้าเพื่อแนบคำสั่งปิดแถวอัตโนมัติ (Auto-Precharge) ไปกับคำขอสุดท้ายของเธรดนั้น จะสามารถเปลี่ยน Row Conflict (42 ns) ให้กลายเป็น Row Closed (28 ns) ได้โดยไม่สูญเสียโอกาสการเกิด Row Hit (14 ns)"

SECTION 3: THEORETICAL BACKGROUND (PART 1/4)

ทฤษฎีพื้นฐาน 1: โครงสร้างภายในของ DRAM Bank และหน้าที่ของ Row Buffer

Slide 07 / 26
🏗️ แผนผังการทำงานภายใน 1 DRAM Bank
🔑 หลักการทำงานสำคัญที่ต้องรู้เกี่ยวกับ DRAM
  • การอ่านข้อมูลจากตัวเก็บประจุ (Capacitor Cell) ไม่สามารถดึงโดยตรงได้: ทุกครั้งที่ต้องการอ่านแม้เพียง 64 ไบต์ DRAM ต้องดึงข้อมูลทั้งแถว (ขนาด 8 KB) ลงมาพักไว้ที่ Row Buffer (Sense Amplifiers) ก่อนเสมอ
  • คำสั่งพื้นฐาน 3 คำสั่งของ DRAM:
    1️⃣ ACTIVATE (ACT): เปิดแถวและโหลดข้อมูลลงสู่ Row Buffer ใช้เวลา $t_{RCD}$
    2️⃣ READ / WRITE (RD/WR): เลือกคอลัมน์จาก Row Buffer ส่งเข้าบัส ใช้เวลา $t_{CL}$
    3️⃣ PRECHARGE (PRE): เขียนข้อมูลกลับและล้าง Row Buffer เพื่อเตรียมเปิดแถวอื่น ใช้เวลา $t_{RP}$
  • ข้อจำกัดทางกายภาพ: ใน 1 แบงก์ มี Row Buffer เพียงชุดเดียว จึงเปิดค้างไว้ได้แค่ ครั้งละ 1 แถวเท่านั้น

ทฤษฎีพื้นฐาน 2: เปรียบเทียบเวลาแฝง 3 สถานะของการเข้าถึง Row Buffer

Slide 08 / 26
⏱️ แผนภาพแกนเวลา (Nanosecond Timeline Comparison) ของการเข้าถึง 3 รูปแบบ
🟢 Row Hit: $t_{CL} = 14\text{ ns}$

เป้าหมายสูงสุดเมื่อคำขอถัดไปเรียกแถวเดิมซ้ำ จึงควร เปิดแถวค้างไว้ (Keep Open) เฉพาะเมื่อมั่นใจว่าจะมีคำขอซ้ำตามมา

🔵 Row Closed: $t_{RCD}+t_{CL} = 28\text{ ns}$

หากรู้ล่วงหน้าว่าคำขอถัดไปจะเปลี่ยนแถว การสั่ง ปิดแถวล่วงหน้า (Auto-Precharge) จะช่วยตัดเวลา $t_{RP}$ ออกไปได้ทันที 14 ns!

🔴 Row Conflict: $t_{RP}+t_{RCD}+t_{CL} = 42\text{ ns}$

เกิดจากการเปิดแถวค้างไว้โดยไม่มีใครใช้ซ้ำ ทำให้คำขอถัดไปต้องมารอ Precharge เอง เสียเวลาแฝงสูงสุดถึง 3 เท่า

หัวใจของการควบคุม Row Buffer คือ: รักษาสีเขียว (14 ns) ให้มากที่สุด และเปลี่ยนสีแดง (42 ns) ให้เป็นสีน้ำเงิน (28 ns) Slide 08 / 26
SECTION 3: THEORETICAL BACKGROUND (PART 3/4)

ทฤษฎีพื้นฐาน 3: เปรียบเทียบข้อดีและจุดอ่อนของนโยบายจัดการ Row Buffer

Slide 09 / 26
นโยบายที่ 1 Open-Page Policy
  • วิธีทำงาน: เปิดแถวค้างไว้ใน Row Buffer เสมอหลังจากอ่านเสร็จ เพื่อรอลุ้นให้คำขอถัดไปเกิด Row Hit ($14\text{ ns}$)
  • เหมาะกับ: งานประมวลผลต่อเนื่อง (Streaming / Sequential Scan) ที่มี Locality สูง
  • จุดอ่อนสำคัญ: ในระบบหลายคอร์ที่คำขอสลับแถวไปมา จะเกิด Row Conflict ($42\text{ ns}$) สูงมาก
นโยบายที่ 2 Closed-Page Policy
  • วิธีทำงาน: สั่งปิดแถวทันที (Auto-Precharge) ทุกครั้งที่อ่านข้อมูลเสร็จ โดยไม่สนใจว่าคำขอถัดไปคือแถวใด
  • เหมาะกับ: งานเข้าถึงแบบสุ่ม (Random Access) เพราะรับประกันเวลาคงที่ที่ $28\text{ ns}$ (ไม่เคยเจอ $42\text{ ns}$)
  • จุดอ่อนสำคัญ: ทำลายโอกาสเกิด Row Hit ($14\text{ ns}$) ทิ้งทั้งหมด แม้คำขอถัดไปจะเรียกแถวเดิมติดกันก็ตาม
นโยบายที่ 3 Timer-Based Policy
  • วิธีทำงาน: เปิดแถวรอไว้เป็นเวลา $\tau$ รอบสัญญาณนาฬิกา (Timeout) หากไม่มีคำขอเข้ามาจึงค่อยสั่งปิดแถว
  • ความตั้งใจ: พยายามประนีประนอมระหว่าง Open-Page และ Closed-Page
  • ทำไมจึงล้มเหลวในยุค Many-Core: คำขอจากเธรดอื่นมักไหลเข้ามาปะทะ (Conflict) ก่อนที่ตัวนับเวลา $\tau$ จะหมดลงเสมอ!
💡 ข้อสรุปสำคัญ (Key Takeaway)

การใช้เกณฑ์คงที่หรือการจับเวลา (Timer) ไม่สามารถปรับตัวทันต่อการสลับเธรดในระดับนาโนวินาทีได้ จึงจำเป็นต้องเปลี่ยนมาใช้ การพยากรณ์ตามจำนวนครั้งการเข้าถึงจริง (Access-Count Prediction)

  • ข้อเสีย: ไม่ใช้ประโยชน์จากแถวที่เปิดอยู่เลย แม้จะมีคำขอแถวเดียวกันรออยู่ในคิวถัดไปก็ตาม
2 FR-FCFS (เน้น Row Hit ก่อน)
  • First-Ready FCFS (Rixner, ISCA'00): ให้คำขอที่ตรงกับแถวที่เปิดอยู่ (Row Hit) ลัดคิวขึ้นมาทำงานก่อนเสมอ
  • ข้อดี: เพิ่มอัตรา Row Hit และแบนด์วิดท์รวมได้สูงมาก
  • ข้อเสียร้ายแรง: เธรดที่อ่านข้อมูลต่อเนื่องจะลัดคิวไปเรื่อยๆ จนเธรดอื่นเกิดอาการค้าง (Thread Starvation) และทำลายความขนานระดับแบงก์
3 PAR-BS (จัดกลุ่มขนาน)
  • Parallelism-Aware Batch Scheduling (Mutlu, ISCA'08): จัดกลุ่มคำขอเป็น Batch และจัดอันดับเธรดให้ทุกแบงก์บริการเธรดเดียวกันพร้อมกัน
  • ข้อดี: แก้ปัญหา Starvation และรักษา Bank-Level Parallelism ได้ดีเยี่ยม
  • ข้อเสียที่ยังเหลืออยู่: ยังคงเปิดแถวค้างไว้เมื่อจบคำขอของเธรดหนึ่ง ทำให้เธรดถัดไปต้องเจอ Row Conflict ($42\text{ ns}$)

SECTION 6: ADAPTIVE ALGORITHM DESIGN (PART 1/2)

เจาะลึก Adaptive Algorithm (1/2): ตารางพยากรณ์ Page History Table (PHT)

Slide 14 / 26
🧠 หลักการเรียนรู้จำนวนครั้งการเข้าถึงซ้ำของแต่ละแถว
  • เมื่อแถวหน่วยความจำ $r$ ในแบงก์ $b$ ถูกเปิดขึ้นมา ตัวควบคุมจะนับจำนวนครั้งที่แถวนี้ถูกเข้าถึงติดต่อกัน เรียกว่า Observed Access Count ($A_{\text{obs}}$)
  • ค่าประวัติของแต่ละแถวจะถูกจัดเก็บในตารางขนาดเล็กชื่อ Page History Table (PHT) ขนาด 512 ช่อง โดยใช้ฟังก์ชันแฮช $\text{idx} = \text{Hash}(b, r) \pmod{512}$
  • แต่ละช่องเก็บค่าพยากรณ์ $\hat{A}(r) \in \{1, 2, 3, 4\}$ (ใช้เพียง 2 บิต) ซึ่งสะท้อนว่าแถวนี้มักถูกเรียกซ้ำกี่ครั้งในการเปิด 1 รอบ
📐 สมการการปรับตัว (Adaptive Learning Rule)

ทุกครั้งที่แถว $r$ ถูกปิดลง ระบบจะนำจำนวนครั้งที่ใช้งานจริงในรอบล่าสุด ($A_{\text{obs}}$) มาปรับค่าพยากรณ์สำหรับรอบถัดไปแบบถ่วงน้ำหนัก (Exponential Moving Average):

$$\hat{A}_{\text{new}}(r) = \text{Clamp}_{[1, 4]}\!\Big(\text{round}\big((1 - \beta)\,\hat{A}_{\text{old}}(r) + \beta \cdot A_{\text{obs}}(r)\big)\Big)$$
  • กำหนดค่าสัมประสิทธิ์การเรียนรู้ $\beta = 0.5$ เพื่อให้ปรับตัวตามการเปลี่ยนเฟสของโปรแกรมได้รวดเร็วภายใน 1–2 รอบ
  • หาก $\hat{A}_{\text{new}}(r) = 1$ หมายความว่าแถวนี้ถูกเรียกแบบสุ่มครั้งเดียวแล้วเลิก (ควรรีบปิดทันที)
การเก็บค่าเป็นจำนวนครั้ง (1 ถึง 4 ครั้ง) ใช้พื้นที่ฮาร์ดแวร์เพียง 2 บิตต่อแถว ประหยัดกว่าตัวนับเวลาแบบ 16 บิตอย่างมาก Slide 14 / 26
SECTION 6: ADAPTIVE ALGORITHM DESIGN (PART 2/2)

เจาะลึก Adaptive Algorithm (2/2): การปรับเกณฑ์ตามคิวและกฎ QAPI

Slide 15 / 26
⚖️ ขั้นที่ 1: ปรับลดเกณฑ์การเปิดแถวตามความคับคั่ง ($R_{\text{conflict}}$)

หากในคิวของ Bank $b$ มีเธรดอื่นรอเข้าถึงแถวอื่นอยู่จำนวนมาก เราจะปรับลดเกณฑ์การปิดแถว $T_{\text{close}}(b,r)$ ลงอัตโนมัติ:

$$R_{\text{conflict}}(b) = \frac{Q_{\text{diff\_row}}(b)}{Q_{\text{total}}(b)}$$
$$T_{\text{close}}(b, r) = \max\!\left(1,\; \left\lfloor \hat{A}(r) \cdot \big(1 - \alpha \cdot R_{\text{conflict}}(b)\big) \right\rfloor\right)$$

เมื่อคิวว่าง ($R_{\text{conflict}} = 0$) จะเปิดแถวรอตามค่าพยากรณ์ $\hat{A}(r)$ เต็มที่ แต่เมื่อคิวแน่น ($R_{\text{conflict}} \to 1$) เกณฑ์จะลดลงเพื่อรีบปิดแถวให้เธรดอื่นเข้าใช้งานได้เร็วขึ้น

🛡️ ขั้นที่ 2: กฎเหล็กมองคิวล่วงหน้า (Queue-Lookahead Precharge Inhibition - QAPI)

เพื่อแก้ปัญหาการสั่งปิดแถวพลาดของอัลกอริทึม ABP เดิม เราเพิ่มวงจรตรวจสอบคิวล่วงหน้าก่อนตัดสินใจสั่งปิดแถวทุกครั้ง:

กลไก QAPI คือจุด Refinement สำคัญที่ช่วยป้องกันไม่ให้ตัวพยากรณ์ปิดแถวทับคำขอที่กำลังต่อคิวอยู่ Slide 15 / 26

เจาะลึก Parallel Algorithm (1/2): การจัดกลุ่มคำขอแบบขนาน (Batching)

Slide 16 / 26
📦 กลไกการสร้าง Batch เพื่อรับประกันความเป็นธรรม (Starvation Freedom)
  • เพื่อไม่ให้เธรดที่ส่งคำขอจำนวนมากลัดคิวเธรดอื่นไปเรื่อยๆ ระบบจะรวบรวมคำขอที่อยู่ในคิวปัจจุบันเข้าสู่ Current Batch (ตั้งค่าบิตสถานะ $B_k = 1$)
  • กำหนดเพดาน Marking Cap ($M_{\text{cap}} = 4$) คืออนุญาตให้แต่ละเธรดนำคำขอเข้าสู่ Batch ได้ไม่เกิน 4 รายการต่อ 1 Bank
  • คำขอที่มาถึงหลังจากสร้าง Batch แล้วจะมีบิต $B_k = 0$ และต้องรอให้คำขอใน Batch ปัจจุบัน ($B_k = 1$) ประมวลผลเสร็จสิ้นก่อนเสมอ
🎨 แผนภาพการแบ่งขอบเขต Batch ภายในคิวของแต่ละ Bank
การทำ Batching ช่วยจำกัดขอบเขตเวลารอสูงสุด (Bounded Delay) ของทุกเธรดในระบบ Slide 16 / 26
SECTION 7: PARALLEL ALGORITHM DESIGN (PART 2/2)

เจาะลึก Parallel Algorithm (2/2): การจัดอันดับเธรดข้ามแบงก์แบบขนาน

Slide 17 / 26
⚡ กฎ Shortest Max-Bank-Load First (รักษา BLP สูงสุด)

เมื่อสร้าง Batch ใหม่ วงจรฮาร์ดแวร์จะคำนวณภาระงานของแต่ละเธรด $i$ ข้ามทุกแบงก์ $b \in \{1..B\}$ พร้อมกันแบบขนาน:

$$L_{\max}(i) = \max_{b \in \{1..B\}} \text{CountBatch}(i, b),\\ \qquad L_{\text{tot}}(i) = \sum_{b=1}^{B} \text{CountBatch}(i, b)$$
  • เธรดที่มีค่า $L_{\max}(i)$ น้อยที่สุด จะได้อันดับความสำคัญสูงสุด (Rank 1) เพราะเป็นเธรดที่ติดงานหน่วยความจำสั้นที่สุด สามารถปลดล็อกให้ซีพียูกลับไปคำนวณต่อได้เร็วที่สุด
  • ทุกแบงก์ใช้ลำดับ Rank เดียวกันนี้ ทำให้คำขอของเธรดอันดับ 1 ที่กระจายอยู่ในหลายแบงก์ ถูกดึงขึ้นมาประมวลผลพร้อมกันทุกแบงก์!
🏆 ลำดับความสำคัญรวมในการคัดเลือกคำขอของแต่ละ Bank

ในแต่ละรอบสัญญาณนาฬิกา ตัวตัดสินใจประจำแบงก์ (Per-Bank Parallel Arbiter) จะเลือกคำขอ $req_k$ ตามลำดับความสำคัญ 4 ขั้นดังนี้:

$$\text{Priority}(req_k, b) = \Big(\; B_k,\;\; H_k^{\text{eff}}(b),\;\; -L_{\max}(\text{tid}_k),\;\; \text{Age}_k \;\Big)$$
  • อันดับ 1 ($B_k = 1$): คำขอที่อยู่ใน Batch ปัจจุบันมาก่อนเสมอ
  • อันดับ 2 ($H_k^{\text{eff}} = 1$): คำขอที่เกิด Row Hit กับแถวที่เปิดอยู่ของเธรดตัวเอง
  • อันดับ 3 ($-L_{\max}(\text{tid}_k)$): คำขอของเธรดที่มีอันดับ Parallel Rank สูงกว่า
  • อันดับ 4 ($\text{Age}_k$): คำขอที่รออยู่ในคิวมานานกว่า
ทุก DRAM Bank รันสมการคัดเลือกนี้ขนานกัน (Parallel Hardware Comparator Tree) ภายใน 1 รอบสัญญาณนาฬิกา Slide 17 / 26

Slide 18 / 26
// อัลกอริทึม AP-PARBS: ประมวลผลขนานกันในทุก DRAM Bank b = 0..B-1 PARALLEL FOR EACH bank $b \in \{0 \dots B-1\}$ DO: if NoMarkedRequestsAcrossAllBanks() then FormNewBatch($M_{\text{cap}}$); ComputeParallelThreadRanks($L_{\max}, L_{\text{tot}}$) // 1. เลือกคำขอชนะเลิศใน Bank b ตามลำดับ Parallel Priority $req^* \leftarrow \arg\max_{req \in \text{Queue}[b]} \big(B_{req},\; H_{req}^{\text{eff}},\; -L_{\max}(\text{tid}),\; \text{Age}_{req}\big)$ // 2. คำนวณเกณฑ์ Adaptive Threshold จากตาราง PHT และความคับคั่งในคิว $r \leftarrow req^*.\text{row}$; $A_{\text{curr}}[b] \leftarrow A_{\text{curr}}[b] + 1$ $T_{\text{close}} \leftarrow \max\big(1, \lfloor \text{PHT}[b, r] \cdot (1 - \alpha \cdot R_{\text{conflict}}(b)) \rfloor\big)$ // 3. UpdatePHT($b, r, A_{\text{curr}}[b]$); $A_{\text{curr}}[b] \leftarrow 0$ else IssueStandardCommandKeepOpen($b, req^*$) // ส่งคำสั่ง READ / WRITE เปิดแถวรอ Hit
✨ จุดปรับปรุงที่ 1: QAPI (`hasMoreSameRow`)

ยับยั้งการปิดแถวทันทีหากตรวจพบว่ายังมีคำขอแถวเดียวกันรออยู่ใน Batch ปัจจุบัน ช่วยลดการสั่งปิดแถวพลาดลงได้ถึง 91%

⚡ จุดปรับปรุงที่ 2: Handover Precharge (`higherRankWaiting`)

เมื่อเธรดปัจจุบันส่งคำขอสุดท้ายเสร็จและมีเธรดลำดับถัดไปรออยู่ ระบบจะแนบคำสั่งปิดแถวล่วงหน้าให้ทันที เธรดถัดไปจึงไม่ต้องเสียเวลา $t_{RP}$ ($14\text{ ns}$)

องค์ประกอบ รายละเอียดพารามิเตอร์ (อ้างอิง Ramulator / JEDEC)
Processor (CPU) 8-Core Out-of-Order CMP, 4.0 GHz, ROB 192 entries
Cache Hierarchy L1D 32KB, L2 512KB per core, L3 Shared 8MB (64B Line)
DRAM Organization Dual-Channel DDR4-3200, 8 Banks/Rank, Row Buffer 8 KB
DRAM Timings $t_{CL} = 14\text{ ns},\; t_{RCD} = 14\text{ ns},\; t_{RP} = 14\text{ ns},\; t_{RAS} = 32\text{ ns}$
AP-PARBS Config Queue 64 entries/Bank, $M_{\text{cap}} = 4$, PHT 512 entries, $\alpha = 0.5$
📐 สมการตัวชี้วัดมาตรฐานในงานวิจัยสถาปัตยกรรมคอมพิวเตอร์

1. ประสิทธิภาพรวมของระบบ (Weighted Speedup):

$$\text{Weighted Speedup} = \sum_{i=1}^{N} \frac{\text{IPC}_i^{\text{shared}}}{\text{IPC}_i^{\text{alone}}}$$

2. ความสมดุลและเป็นธรรม (Harmonic Speedup & Max Slowdown):

$$\text{Harmonic Speedup} = \frac{N}{\sum_{i=1}^{N} \left(\frac{\text{IPC}_i^{\text{alone}}}{\text{IPC}_i^{\text{shared}}}\right)}, \qquad \text{Max Slowdown} = \max_{i} \frac{\text{IPC}_i^{\text{alone}}}{\text{IPC}_i^{\text{shared}}}$$
อ้างอิงตัวจำลองหน่วยความจำมาตรฐาน Ramulator (Kim, Yang, Mutlu - IEEE CAL 2016) Slide 21 / 26

SECTION 12: CONCLUSION & FUTURE WORK

สรุปผลการวิจัย คุณูปการสำคัญ และแนวทางการพัฒนาต่อยอดในอนาคต

Slide 25 / 26
1 ตอบคำถาม RQ1 & RQ2

การพยากรณ์ด้วยจำนวนครั้งการเข้าถึง (Access-Based PHT) ร่วมกับการตรวจสอบคิวล่วงหน้า (QAPI) แก้ปัญหาการสั่งปิดแถวผิดจังหวะของระบบเดิมได้อย่างสมบูรณ์

2 ตอบคำถาม RQ3

การผสานเข้ากับ Parallel Batch Scheduling ช่วยจัดกลุ่มคำขอของเธรดเดียวกันให้เกิด Row Hit ต่อเนื่อง แล้วสั่ง Auto-Precharge ทันทีเมื่อเปลี่ยนผ่านไปยังเธรดถัดไป

3 แนวทางต่อยอดในอนาคต

สามารถขยายผลสู่หน่วยความจำ HBM3 (High Bandwidth Memory) สำหรับชิปประมวลผล AI/LLM ที่มีถึง 32–64 Pseudo-channels รวมถึงระบบ CXL Memory Pooling

📌 สรุปภาพรวมการทำ Algorithm Refinement ในโปรเจกต์นี้

งานวิจัยนี้ได้พิสูจน์ให้เห็นว่า การนำ Adaptive Algorithm (การพยากรณ์โหมดหน้าหน่วยความจำ) และ Parallel Algorithm (การจัดตารางคำขอข้ามแบงก์แบบขนาน) มาปรับปรุงและเชื่อมโยงสัญญาณสถานะเข้าด้วยกัน สามารถยกระดับประสิทธิภาพของระบบจัดการ RAM ได้เหนือกว่าการใช้อัลกอริทึมใดอัลกอริทึมหนึ่งเพียงลำพังอย่างชัดเจน
